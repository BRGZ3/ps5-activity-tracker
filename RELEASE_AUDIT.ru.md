# Аудит релиза Playlog v1.0

[English version](RELEASE_AUDIT.md)

Дата аудита: 2026-08-06

Статус: `PUBLIC v1.0 / KNOWN LIMITATIONS`

Рабочая связка dashboard + runtime проверена на целевом сценарии PS5 4.50.
Релиз v1.0 публикуется с известными ограничениями жизненного цикла runtime,
обновлений, приватности LAN и воспроизводимости сборки. Этот файл фиксирует
решения, которые нужно сохранить при быстрых обновлениях v1.0.

## P0 — приоритеты усиления

### 1. Чистое публичное дерево

В рабочем каталоге нельзя публиковать реальные `summary.json`,
`probe-events.jsonl`, `tracker-state*.bin`, backup, IP консоли, историю игр,
`.omx` и промежуточные сборочные каталоги. В публичном репозитории оставлены
только исходники, тесты и документация. Реальные PKG/ELF должны быть GitHub Release
Assets, а не частью истории исходников.

### 2. Эксклюзивность runtime и режимов

Текущий PID-файл не является настоящей блокировкой: второй экземпляр может
перезаписать его и начать писать те же файлы. Переключение etaHEN ↔ SM+/PLK
также может оставить противоположный автозапуск. Это способно привести к двум
процессам, конфликту порта и повреждению истории.

Нужны атомарная блокировка процесса, подтверждение остановки
старого экземпляра и транзакционное удаление противоположного автозапуска.

### 3. Транзакционное обновление и restore

Обновление dashboard и ELF сейчас выполняется пофайлово. Ошибка после первой
замены оставляет смешанные версии, а backup сохраняет статистику, но не
предыдущие программные файлы. Restore тоже заменяет sidecar-файлы
последовательно.

Нужны staging, проверка всего комплекта, rollback-журнал, commit-marker только
после проверки и сохранение предыдущей рабочей версии runtime/dashboard.

### 4. Ошибки persistence должны быть видимыми

Ошибки записи состояния сейчас игнорируются перед созданием backup. Нужно
возвращать статусы `write_state`/`write_summary`, не считать backup успешным при
устаревшем состоянии и показывать degraded state в dashboard.

### 5. Production carrier должен быть однозначным

Production-код не должен автоматически подбирать старые `ACTV00003`, `ACTV00005`
или `ACTV00006`. Production использует только `ACTV00002`; миграция старых
тестовых сборок должна быть отдельным явным сценарием. Также нужен запрет
понижения версии и проверка целевого продукта/schema.

### 6. Приватность LAN

Read-only запрещает удалённым клиентам POST, но не защищает историю от
просмотра. Сервер слушает LAN без аутентификации, а wildcard CORS упрощает
чтение данных чужой страницей.

В следующем обновлении нужен минимум один из вариантов:

1. loopback по умолчанию + явное включение LAN;
2. случайный токен для LAN-чтения;
3. токен/nonce в custom header для каждой mutating-операции.

Во всех случаях порт нельзя публиковать в интернет.

## P1 — backlog быстрых обновлений

- Сделать сборку воспроизводимой: runtime должен собираться из исходников, а
  не браться из случайного старого `.elf`; зависимости LibProsperoPKG и Docker
  должны быть зафиксированы или явно указаны в release notes.
- Добавить CI для host-тестов, проверки публичного дерева, JS syntax и
  согласованности версий.
- Синхронизировать версии: README, footer dashboard, runtime, carrier и PKG
  metadata должны показывать один релизный набор.
- Переписать старый `activity-probe/README.md`, убрать инструкции про probe
  v0.4.0/plugin v1.30 и удалить из активной документации команды для
  отсутствующего корневого `ps5_tracker.py`.
- Зафиксировать таблицу совместимости: firmware, etaHEN/SM+/PLK, способ
  запуска, дата и результат теста. Не заявлять поддержку шире фактически
  проверенных конфигураций.
- Добавить `LICENSE`, `SECURITY.md`, `CONTRIBUTING.md` и `CHANGELOG.md`.

## P2 — дальнейшее сопровождение

- ротация неограниченного `probe-events.jsonl`;
- настоящая системная timezone/DST-поддержка вместо fallback Moscow;
- профили пользователей;
- экспорт CSV/JSON;
- классификация диагностических ошибок;
- отдельная вкладка диагностики;
- расширенная миграция бинарного состояния.

## Критерий будущего hardening-релиза

Для усиленного релиза должны пройти чистая установка и обновление в обоих
режимах, одновременный запуск должен быть невозможен, частичный update/restore
должен откатываться, LAN-доступ должен иметь явную политику доверия, а
`python3 -m unittest discover -s tests -v` должен работать из чистого clone без
дополнительного `PYTHONPATH`.
